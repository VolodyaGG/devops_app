## Что сделано

Настроен полный CI/CD пайплайн с автоматическим деплоем с использованием GitOps

## Запуск

Для инициализации Argo CD в кластере (один раз):

```bash
kubectl apply -f k8s/argocd-app.yaml
kubectl apply -f k8s/image-updater.yaml
```

После этого деплой происходит автоматически при каждом пуше - CI собирает и пушит образ, Argo CD подхватывает изменения сам по изменению latest digest

Чтобы войти в Argo CD, пропишите команду на мастер ноде (10.184.0.116 под юзером master):
```bash
kubectl get secret argocd-initial-admin-secret -n argocd -o jsonpath="{.data.password}" | base64 -d
```

## Архитектура CI/CD

Пайплайн собирает образ, прогоняет тесты, сканирует на уязвимости и пушит на Docker Hub с тегом `latest`. После пуша ждёт 150 секунд и проверяет, что приложение живо через smoke test на `https://cbr-app.local/info`. Затем запускается DAST сканирование через OWASP ZAP

## Почему такой подход

CI не обращается к кластеру напрямую и не надо передавать никаких kubeconfig в пайплайне. Argo CD сам следит за репозиторием и синкает helm чарт из `k8s/cbr-app`. Argocd Image Updater раз в 2 минуты проверяет digest тега `latest` на Docker Hub и если образ изменился, автоматически раскатывает новую версию. Инфраструктура меняется только через master, образ обновляется с любой ветки, если выполнены соответствующие правила в пайплайне

# ДЗ 6
## Что сделано

Приложение задеплоено в Kubernetes кластер. Для деплоя используется Helm чарт, который темплейтизирует манифесты и позволяет переопределять параметры через переменные окружения

## Запуск
Переменные окружения: PORT, HOST, DOCKER_LOGIN
Для деплоя приложения определить переменные окружения (опционально, переменные по умолчанию определены) и запустить скрипт `deploy.sh`:

```bash
export IMAGE_TAG=your-tag # пример
chmod +x k8s/deploy.sh
./k8s/deploy.sh
```

Для настройки HTTPS на клиентской машине (нужен доступ к VPN):

```bash
chmod +x k8s/tls_install.sh
./k8s/tls_install.sh
```

Обратиться к кластеру можно будет по адресу https://cbr-app.local/info

## Архитектура

Входящий трафик принимает nginx ingress controller и направляет его в ClusterIP сервис, который балансирует трафик между подами. Приложение запускается в четырех репликах на разных воркер нодах - это обеспечивает отказоустойчивость при падении одной ноды

## Почему такой подход

Helm выбран для темплейтизации манифестов — один чарт покрывает разные окружения, поддерживает откат через `helm rollback` и деплой одной идемподентной командой

ClusterIP для сервиса выбран намеренно — сервис не должен быть доступен снаружи напрямую, единственная точка входа это ingress.

`podAntiAffinity` с preferred режимом гарантирует что поды будут на разных нодах, но не блокирует деплой если нод не хватает.

HTTPS реализован через mkcert — локальный CA сертификат распространяется через скрипт `tls_install.sh`.

# Создание кластера Kubernetes с помощью Ansible

## Структура проекта

Кластер разворачивается через 6 ролей:

- preps — подготовка нод
- crio — установка container runtime
- k8s_base — установка пакетов kubeadm/kubelet/kubectl
- k8s_master — инициализация мастер ноды
- k8s_worker — подключение воркеров к кластеру
- calico — установка CNI плагина

Все роли кроме calico покрыты MOLECULE тестами (так как для тестирования нужен готовый кластер)

## Этапы создания

### 1. Подготовка нод (роль preps)

На всех нодах выполняется обновление apt кэша, установка базовых зависимостей (curl, ca-certificates, gnupg), отключение swap (требование kubeadm), настройка hostname

### 2. Установка CRI-O (роль crio)

Загружаются kernel модули overlay и br_netfilter, настраиваются sysctl параметры для сетевого моста, добавляется репозиторий и устанавливается CRI-O. Сервис запускается и включается в автозапуск

### 3. Установка k8s компонентов (роль k8s_base)

Добавляется репозиторий pkgs.k8s.io, устанавливаются kubeadm, kubelet, kubectl. Пакеты фиксируются через apt-mark hold чтобы предотвратить случайное обновление

### 4. Инициализация мастера (роль k8s_master)

Запускается kubeadm init с указанием pod network CIDR для Calico и CRI socket. Настраивается kubeconfig для пользователя. Сохраняется join команда для воркеров

### 5. Подключение воркеров (роль k8s_worker)

Каждый воркер выполняет kubeadm join с указанием CRI socket CRI-O

### 6. Установка Calico (роль calico)

Применяется манифест Calico версии 3.31.5. После применения ожидается готовность calico-node подов на всех нодах

## Встреченные проблемы и решения

### Проблема 1: Истёкший SSL сертификат pkgs.k8s.io

При добавлении репозитория kubernetes apt-get update падал с ошибкой SSL certificate has expired. Официальный репозиторий pkgs.k8s.io имел истёкший сертификат

Переключился на зеркало OpenBuildService download.opensuse.org которое является источником для pkgs.k8s.io. Ключ репозитория скачивается отдельно и конвертируется через gpg --dearmor

### Проблема 2: Port 6443 is in use при повторном kubeadm init

При повторном прогоне тестов molecule kubeadm init падал с ошибкой что порт 6443 занят — предыдущий api-server не успевал завершиться после kubeadm reset

В destroy добавлена пауза 30 секунд после reset, принудительное завершение процесса на порту через fuser -k 6443/tcp, остановка kubelet и размонтирование примонтированных директорий kubelet

### Проблема 3: Device or resource busy при удалении /var/lib/kubelet

После reset kubelet директория не удалялась из-за примонтированных томов

Добавлен таск размонтирования всех точек монтирования внутри /var/lib/kubelet перед удалением директории

### Проблема 4: ping permission denied внутри busybox пода

Запуск ping 8.8.8.8 внутри busybox пода давал ошибку permission denied несмотря на настройку net.ipv4.ping_group_range. Проблема была в том что CRI-O с runtime crun не включает NET_RAW capability по умолчанию

В конфигурацию CRI-O добавлен явный список default capabilities включающий NET_RAW

### Проблема 5: Ansible Vault не подхватывал зашифрованный пароль

При использовании ansible-vault для хранения `ansible_become_pass` пароль не подтягивался в molecule несмотря на правильно зашифрованный файл. Проблема была в структуре — файл vault.yml лежал в корне molecule/default/ и molecule его не видел как inventory переменные.

Изменена структура директорий — vault.yml перенесён в molecule/default/group_vars/all/vault.yml. После этого molecule стал корректно подхватывать зашифрованные переменные при запуске с ANSIBLE_VAULT_PASSWORD_FILE

## Как запустить?
1. Добавить в корень проекта файл с паролем от виртуалок .vault_pass (пароль стандартный)
2. Для запуска тестов: перейти в директорий роли и прописать `ANSIBLE_ASK_VAULT_PASS=True molecule test`, если возникнет необходимость проверить работу можно написать в личку в тг: `@itwastoohard` я отправлю пароль

# ДЗ 4
## Ansible-роли для Kubernetes

В рамках ДЗ4 были собраны 4 роли для подготовки Kubernetes-узла на Debian/Ubuntu:

- vlaptev.k8s.crio - устанавливает CRI-O, подключает нужный репозиторий, загружает модули ядра и настраивает sysctl.
- vlaptev.k8s.kubeadm - устанавливает kubeadm, добавляет Kubernetes-репозиторий и фиксирует пакет через hold.
- vlaptev.k8s.kubelet - устанавливает kubelet, подключает репозиторий Kubernetes и также удерживает пакет от случайного обновления.
- vlaptev.k8s.kubectl - устанавливает kubectl, создает .kube для пользователя и добавляет bash-completion.

### Зависимости

- Ansible
- коллекция community.general
- коллекция ansible.posix
- Debian/Ubuntu с пакетным менеджером apt
- Docker и Molecule для локальной проверки роли

### Переменные роли

- crio_version
  Значение по умолчанию: "1.32"
  Используется в роли crio для выбора версии CRI-O.

- k8s_version
  Значение по умолчанию: "1.32"
  Используется в ролях kubeadm, kubelet и kubectl для выбора версии Kubernetes-репозитория.

- k8s_user
  Значение по умолчанию: "worker"
  Используется для создания пользователя и директории .kube.

### Пример использования в playbook

```yaml
---
- name: Install k8s components
  hosts: k8s_cluster
  become: true
  roles:
    - role: vlaptev.k8s.crio
    - role: vlaptev.k8s.kubeadm
    - role: vlaptev.k8s.kubelet
    - role: vlaptev.k8s.kubectl
```

### Vault

Зашифрован пароль для входа на ВМ. Переменные вынесены в inventory/group_vars/all/vault.yml, а в inventory/group_vars/all/vars.yml они подключаются как обычные переменные, например для ansible_password и ansible_become_password

В ansible.cfg настроен параметр vault_password_file = .vault_pass, поэтому пароль для расшифровки Vault читается из локального файла .vault_pass

### Проверка

Для каждой роли добавлен отдельный Molecule-сценарий default. Проверка запускается в Docker-контейнере и подтверждает, что нужный пакет установлен, бинарник присутствует в системе и основная команда crio, kubeadm, kubelet или kubectl успешно запускается

# ДЗ 3
## Advanced CI
### 1. Структура пайплайна

Пайплайн разделён на два файла: основной `.gitlab-ci.yml` из 6 стадий и дочерний `.deploy-config.yml` из 3 стадий, который запускается через `trigger` и отвечает исключительно за деплой и проверки после него.

### 2. Стадии основного пайплайна

#### `lint_and_sast`

Линтеры `ruff` и `hadolint` объединены в один джоб `lint` на базе `nixos/nix` — оба инструмента устанавливаются через `nix-shell` из одного образа.

Параллельно работает джоб `sast`, который запускает Bandit — статический анализатор безопасности Python-кода. Результат публикуется в GitLab Security Dashboard.

#### `test`

Сборка `build_dev` ждёт успешного завершения `lint` и `sast` — тесты не стартуют, если на предыдущем шаге что-то пошло не так.

#### `build_and_push`

Production-образ собирается только после прохождения всех тестов. Тег образа формируется автоматически: для веток используется SHA коммита, для тегов вида `v*` — сам тег.

#### `sca`

После публикации образа в Docker Hub он сразу проверяется через Trivy. Сканируются только уязвимости с доступным фиксом уровня HIGH и CRITICAL — если такие найдены, пайплайн останавливается. Отчёт сохраняется в GitLab.

#### `release`

При пуше тега вида `v*` автоматически создаётся GitLab Release с changelog. Список изменений генерируется из коммитов между текущим и предыдущим тегом. Чтобы git видел всю историю в CI, установлен полный клон репозитория и явное подтягивание тегов перед генерацией.

#### `trigger_deploy`

Деплой запускается как дочерний пайплайн. Пуш в `master` автоматически деплоит на staging, пуш тега — на production. Также доступен ручной запуск через Web UI с выбором окружения и тега.

### 3. Дочерний пайплайн `.deploy-config.yml`

#### `deploy`

Подтягивает нужный образ и поднимает его через `docker-compose.hardened.yml` на раннере целевого окружения.

#### `smoke_test`

После деплоя проверяет, что приложение живо и отвечает ожидаемым сервисным именем на `/info`.

#### `dast_zap`

Динамическое тестирование безопасности через OWASP ZAP. Сканер получает OpenAPI-спецификацию приложения и проверяет каждый эндпоинт. Запускается только на staging и работает в режиме наблюдения — пайплайн не падает, но отчёт с находками всегда сохраняется.

### 4. Pre-commit хуки

Настроена локальная защита от случайной утечки секретов через Gitleaks — сканер проверяет каждый коммит на наличие токенов, паролей и ключей API ещё до того, как они попадут в репозиторий.

Установка:

```sh
brew install pre-commit
pre-commit install
```

### 5. Dockerfile

Добавлен отдельный `builder`-стейдж: Poetry устанавливается только там и не попадает в финальный образ — в `development` и `production` копируются только готовые `requirements.txt`. В production-стейдже системные пакеты обновляются при сборке. Во всех стейджах приложение запускается от непривилегированного пользователя.

### 6. Vulnerabilities

Во время выполнения сканиррования с помощью Trivy были исправлены уязвимости, связанные со стандартным набором пакетов в python:3.12-slim, было исправлено с помощью обновления пакетов.

CVE-2026-34591 (Poetry): в образе была установлена версия Poetry 2.3.2, имеющая статус HIGH. Решение — обновление до 2.3.3 и полное удаление Poetry из финального образа.

После SAST анализа Был заменен стандартный xml.etree.ElementTree на defusedxml, так как он уязвим к атакам на XML-injection.

Разработан `docker-compose.yml`. Он задает сервис "app", который запускает команду "python main.py". Сервис работает в режиме только для чтения и использует tmpfs для временных файлов. Также задаются переменные окружения и проброс портов.
Затем создан новый файл `docker-compose.hardened.yml` с новыми настройками безопасности: ограничение прав доступа, отключение привилегий, ограничение ресурсов, отключение коммуникации между контейнерами.

Также приложение загружено на docker hub: https://hub.docker.com/repository/docker/volodyagg/client_server_app

# Currency Service — Домашнее задание №2

Сервис на FastAPI, который предоставляет актуальные курсы валют с помощью API Центрального Банка РФ.

`GET /info`

Возвращает информацию о версии, названии сервиса и авторе.
*Данные берутся из переменных окружения (.env).*

`GET /info/currency`

**Параметры:**
* `date` (optional): Дата в формате `YYYY-MM-DD`.
* `currency` (optional): Код валюты (например, `eur`).

**Логика обработки:**
* Если `date` не указан — выдаются данные на текущий день.
* Если `currency` не указан — выдается полный список всех валют в ключе `currencies`.

### Технологи
* **Python 3.12+**
* **FastAPI**
* **Requests**
* **ElementTree**
* **Pyproject.toml**

### Старт

1. Установка зависимостей:
   Все необходимые библиотеки подтянутся из файла конфигурации:
   ```
   pip install .
   ```

2. Настройка переменных окружения:
    Создайте файл .env в корне проекта:
    ```
    PORT=8000
    VERSION=1.0.0
    AUTHOR=v.laptev
    ```
